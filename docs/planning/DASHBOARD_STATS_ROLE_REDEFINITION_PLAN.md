# 대시보드 vs 통계 페이지 역할 재정의 기획서

> **작성 방식**: `.claude/skills/design/SKILL.md`에 새로 반영한 Playwright 자가 검증 스킬을
> 사용해 `/`(대시보드)와 `/stats`(통계) 두 화면을 실제로 로그인해 렌더링한 뒤 캡처·비교했다.
> 코드만 읽고 추정한 것이 아니라, 실제 화면에 어떤 위젯이 어떤 모양으로 겹쳐 있는지 확인한
> 결과를 근거로 작성했다. 원문 근거는 `UI_IMPROVEMENT_PLAN.md`/`UI_IMPROVEMENT_DESIGN.md`의
> 2.10("장기 — 방향만")이며, 본 문서가 그 방향을 실제 화면 구조까지 구체화한 후속 기획서다.
>
> **본 문서는 기획(설계)까지만 다룬다. 구현은 별도 커밋으로 진행한다.**
>
> **개정**: `grill-me` 스킬로 압박 검증을 거쳐 개정했다 — §5의 "한 줄 추가" 표현을 정정하고,
> §6의 "난이도 차이 미미" 주장을 실제 CSS로 반박·재작성했으며, 우선순위 근거(§0)와 빈 상태
> 처리(§3), design 스킬 프리뷰 순서(§7)를 보강했다.

## 0. 왜 지금인가 (우선순위 근거)

`UI_IMPROVEMENT_PLAN.md` 장기 과제 중 사이드바 IA 재편·반응형 검증은 이미 완료됐고, 남은 건
이 항목과 신고 워크플로우 재설계·이미지 안정성 조사다. 이 항목을 먼저 다루는 근거는 난이도가
낮다는 것만이 아니다 — **대시보드는 관리자가 로그인 후 가장 먼저·가장 자주 보는 화면인데,
지금 그 절반이 통계 페이지와 완전히 같은 내용을 보여준다.** 같은 정보를 두 번 보여주는 화면은
운영자가 "이 숫자를 어디서 봐야 하는지" 판단 비용을 매번 지불하게 만든다 — 반면 신고
워크플로우·이미지 안정성은 노출 빈도가 낮은 화면(신고 발생 시에만, 콘텐츠 표시 이상 발생
시에만)이라 상대적으로 급하지 않다.

## 1. 실측 결과 — 두 화면은 실제로 겹친다

`/`와 `/stats`를 나란히 캡처해 비교한 결과, 코드 리뷰에서 예상했던 것보다 겹침이 명확했다:

| 위젯 | 대시보드(`/`) | 통계(`/stats`) | 판정 |
|---|---|---|---|
| 사진 업로드 추이 | "최근 7일 사진 업로드" 바 차트(일자별 photos) | "기간별 추이" 라인 차트에 `photos` 시리즈 포함(7/30/90일 탭) | **완전 중복** — 대시보드 쪽은 통계 쪽의 부분집합(7일 고정) |
| 인기 사진 랭킹 | "인기 사진 TOP 5" (좋아요순 고정) | "인기 사진 TOP 10" (좋아요/저장/공유 정렬 전환 가능) | **완전 중복** — 대시보드 쪽이 그대로 통계 쪽의 앞 5개 |
| KPI 총계 | 전체 회원·전체 사진 (누적 총량) | 사진 업로드(30일)·신규 가입(30일)·문의 접수(30일) (기간 합계) | 성격이 달라 중복은 아니지만, "총량"과 "기간 합계"가 각 화면에 분산돼 있어 어느 화면에서 뭘 봐야 하는지 직관적이지 않음 |

반면 대시보드에 이미 있는 **촬영 예약 캘린더·이번 주 촬영 예약·최근 활동·최근 문의 5건**, KPI의
**오늘 신규 문의·미읽음 문의·오늘 예약·미확정 예약**은 모두 "지금 확인/처리가 필요한 것"
성격이라 겹치지 않는다 — 이 부분은 그대로 둔다.

## 2. 역할 재정의 원칙 (기존 방향 재확인)

- **대시보드 = 오늘 당장 확인할 이상 신호·액션 필요 항목**. "지금 몇 개나 밀려 있는가/처리해야
  하는가"에 답한다.
- **통계 = 기간별 추이·랭킹 분석**. "지난 N일간 어떻게 변해왔는가/무엇이 잘되고 있는가"에
  답한다.
- 위 표에서 완전 중복으로 판정된 두 위젯(7일 업로드 차트, 인기 사진 TOP5)은 **대시보드에서
  제거**하고 통계 페이지로 일원화한다. 삭제가 아니라 "한 곳에서만 보여준다"는 원칙이다.

## 3. 대시보드 목표 구성

### 제거
- "최근 7일 사진 업로드" 바 차트 전체 (`DashboardPage.jsx`의 `daily` 상태·API 호출 포함 제거)
- "인기 사진 TOP 5" 패널 전체 (`topPhotos` 상태·API 호출 포함 제거)

### 대체 — 심사 대기 포트폴리오
기존 문서(2.10)가 제안했던 세 후보(미확정 예약 수, 미읽음 문의 수, 심사 대기 포트폴리오) 중
**미확정 예약·미읽음 문의는 이미 KPI 카드로 존재**한다. 유일하게 빠진 "심사 대기 포트폴리오"를
새 KPI 카드로 추가해 6칸 그리드를 유지한다.

```
KpiCard: icon="📋" label="심사 대기 포트폴리오" value={summary?.pendingPortfolios} to="/portfolios?status=PENDING"
```

제거되는 두 위젯이 차지하던 2칸 영역에는 **심사 대기 포트폴리오 미리보기 리스트**(표지 이미지 +
작가명 + 제출일, 최대 5건, `PortfolioListPage`의 카드 축약형)를 배치해 "지금 승인/반려 처리가
필요한 것"을 바로 보여준다 — 클릭 시 `/portfolios?status=PENDING`으로 이동(`PortfolioListPage`가
이미 `useSearchParams`로 `status` 쿼리를 읽으므로 프론트 추가 작업 없이 바로 동작함, 코드 확인됨).

**빈 상태**: 심사 대기 건이 0건일 때(전부 처리 완료 시 실제로 발생 가능 — 현재 시드 데이터는
6개 중 2개가 PENDING이라 개발 중엔 안 보이는 케이스) "심사 대기 중인 포트폴리오가 없습니다"
문구 + 아이콘으로 대체한다. 이 화면 전용 신규 empty-state이므로 문구를 새로 작성해야 한다.

### 유지
- KPI 6칸(전체 회원, 전체 사진, 오늘 신규 문의, 미읽음 문의, 오늘 예약, 미확정 예약) + 신규
  "심사 대기 포트폴리오" 1칸 → **7칸**으로 확장하거나, "전체 회원/전체 사진"처럼 순수 누적
  총량 성격의 카드 2개를 통계 페이지로 옮기고 6칸을 유지하는 두 가지 옵션이 있음(§6 참고 —
  실제 코드 기준으로는 6칸 유지 쪽이 더 가볍다).
- `ActivityFeed`, `BookingCalendar`, `WeeklyBookingList`, "최근 문의 5건" 테이블 — 그대로 유지.

## 4. 통계 페이지 목표 구성

- "기간별 추이" 라인 차트, "인기 사진 TOP 10" 테이블은 이미 대시보드보다 상위 호환이므로
  변경 없음 — 대시보드 쪽 중복 위젯이 빠지면 통계 페이지가 유일한 추이·랭킹 소스가 된다.
- 대시보드에서 옮겨올 만한 것: 없음(대시보드 쪽 위젯은 삭제이지 이관이 아님 — 이미 통계 쪽에
  상위 호환 버전이 존재하기 때문).
- 참고: 이번 캡처에서 "기간별 추이" 30일 뷰의 `문의 접수` 라인이 그래프 상 거의 보이지 않는
  현상을 발견했다(데이터 자체가 특정 구간에 몰려 있어 그런 것으로 보이나 확정 원인 조사는
  본 문서 범위 밖). 본 재정의와 별개로 통계 페이지 차트 가독성 이슈로 별도 기록해둔다.

## 5. 백엔드 의존성

`pendingPortfolios` 필드 하나만 필요하며, 신규 쿼리 없이 기존 코드로 즉시 구현 가능함을 코드로
확인했다:

- `PortfolioRepository`에 이미 `countByStatus(PortfolioStatus status)`가 존재(`PortfolioRepository.java:29`).
- `StatsSummaryDto`에 `pendingPortfolios` 필드 추가.
- `AdminStatsService`는 현재 `PortfolioRepository`를 주입받고 있지 않다(코드 확인 —
  `memberRepository`/`photoRepository`/`inquiryRepository`/`bookingRepository`만 존재).
  `@RequiredArgsConstructor`라 생성자를 직접 손볼 필요는 없지만, 정확히는 **(1) 필드 선언
  1줄 + (2) summary 빌더에 `portfolioRepository.countByStatus(PortfolioStatus.PENDING)` 1줄**,
  총 2곳 변경이다 — "한 줄"은 과장된 표현이었다.
- 프론트 `getApi('/admin/stats/summary')` 응답 스펙만 확장되므로 기존 소비처(대시보드) 외 영향
  없음.

이 정도 규모면 "여러 백엔드 API 신설이 필요"했던 신고 워크플로우 재설계(2.2)나 인프라 조사가
필요한 이미지 안정성(2.12)과 달리, **중기 과제 수준으로 바로 착수 가능**하다고 판단한다.

## 6. 남은 결정 사항 (구현 착수 전 확인 필요)

- **KPI 7칸 확장 vs 6칸 유지, 난이도는 같지 않다** — `DashboardPage.css`의 `.kpi-grid`는
  `grid-template-columns: repeat(6, 1fr)` + 브레이크포인트 3개(1280px→3열, 768px→2열,
  480px→gap만 축소)로 전부 하드코딩돼 있다(코드 확인). 두 옵션의 실제 비용:
  - **7칸 확장**: `.kpi-grid`와 3개 브레이크포인트를 전부 다시 짜야 한다(7은 3·2로 고르게
    안 나뉘어 마지막 줄에 홀수 칸이 남는 문제도 새로 풀어야 함).
  - **6칸 유지(총량 카드 2개를 통계로 이관)**: 대시보드 그리드는 손대지 않아도 되지만, 대신
    `StatsPage`에 KPI 카드 2개를 새로 배치할 자리와 스타일을 만들어야 한다.
  → 순수 프론트 작업량으로는 **6칸 유지 쪽이 더 가볍다**(기존 그리드 불변, 통계 페이지에
  이미 있는 `stats-kpi-grid` 패턴에 카드 2개만 추가). 다만 "대시보드 첫 화면에서 회원·사진
  총량을 못 본다"는 사용성 트레이드오프는 여전히 남아 있어 최종 선택은 사용 빈도 판단이
  필요하다 — **난이도가 아니라 이 지점에서만 사용자 판단이 필요하다.**
- 심사 대기 포트폴리오 미리보기 리스트를 대시보드에 바로 심을지, KPI 카드만 추가하고 리스트는
  생략할지(더 가벼운 구현) — 화면 밀도와 구현 범위의 트레이드오프.

## 7. 검증 계획 (구현 시)

**순서 정정**: CLAUDE.md Working Rules #5("UI/디자인 작업은 `design` 스킬 필수 사용")에 따라,
미리보기 리스트·KPI 재배치 같은 레이아웃 결정은 코드를 다 짜고 나서가 아니라 **`design`
스킬로 먼저 목업 → Playwright PREVIEW → 확정된 레이아웃만 실제 페이지에 반영**하는 순서로
진행한다. §3·§6에서 이미 정한 것은 "무엇을 넣을지"(내용)까지고, "어떻게 배치할지"(정확한
크기·간격·빈 상태 문구 톤)는 이 PREVIEW 단계에서 확정한다.

구현 완료 후에는 `/`, `/stats`를 데스크톱(1440px)·모바일(375px) 양쪽에서 Playwright로 다시
캡처해 (1) 중복 위젯이 실제로 사라졌는지 (2) 새 KPI·리스트가 실데이터로 정상 렌더되는지 (3)
심사 대기 0건일 때 빈 상태가 의도대로 보이는지 (4) 선택한 그리드 옵션(6칸 유지 또는 7칸
확장)이 반응형에서 깨지지 않는지 직접 확인한 뒤 커밋한다.
