# 디자인 자가 검증(Playwright Self-Check) 도입 기획서

> **범위**: Claude가 생성하는 화면의 완성도를 높이기 위한 워크플로우 개선 1건("3가지 스킬" 중
> 1번 — Playwright 자가 점검) 도입. 2번(Taste Skill 대응 — Design 플러그인)·3번(Image to Code)은
> 본 문서 범위 밖.

## 1. 문제

Claude가 생성한 화면이 "촌스럽다"는 인상을 주는 가장 흔한 원인은 **코드만 보고 실제 렌더링
결과를 눈으로 확인하지 않은 채 완료 보고를 하는 것**이다. 코드 리뷰로는 다음을 잡아낼 수 없다:

- CSS 변수 오타·존재하지 않는 토큰 참조(예: 이번 세션에서 발견한 `--color-text-2` — 상속으로
  우연히 렌더링되어 코드만 봐서는 정상처럼 보임)
- 좁은 화면에서의 레이아웃 붕괴(플렉스 아이템이 `min-width: 0` 없이 넘침, 테이블 셀 줄바꿈으로
  가로 스크롤 패턴이 무력화되는 등)
- 라이트/다크 모드 중 한쪽에서만 발생하는 대비 문제
- 여백·정렬이 수치상으로는 맞지만 시각적으로 어색한 경우

기존 `.claude/skills/design/SKILL.md`의 워크플로우에는 5단계(PREVIEW, Playwright 스크린샷)가
이미 있었지만 **"서버가 이미 기동 중일 때만 수행, 아닐 경우 빌드 성공으로 완료 보고"** 라는
예외 조항 때문에 사실상 생략 가능한 선택 단계였다.

## 2. 해결 방향

`design` 스킬의 5단계를 **생략 불가 필수 단계**로 승격한다.

- dev 서버가 안 떠 있으면 백그라운드로 직접 기동(`npm start`)한 뒤 진행 — "서버가 없으니 생략"을
  더 이상 허용하지 않는다.
- Chromium은 이 환경에 사전 설치되어 있다(`/opt/pw-browsers/chromium`), 별도 설치 불필요.
- 스크린샷을 찍는 데서 끝내지 않고 **직접 확인 → 문제 발견 시 코드로 되돌아가 수정 → 재스크린샷**
  루프를 완료 조건으로 삼는다.
- 데스크톱(1440px) 스크린샷만으로는 반응형 붕괴를 놓칠 수 있으므로, 레이아웃 변경이 있는
  작업은 모바일(375px) 뷰포트도 함께 확인한다.

`.claude/skills/design/SKILL.md`의 워크플로우 섹션을 이 방향으로 수정 완료(본 기획서와 함께
커밋).

## 3. 이미 실증된 효과

이번 세션에서 별도 요청 없이 반응형 감사를 진행하며 이 방식(Playwright로 직접 열어 확인)을
그대로 적용한 결과, 코드 리뷰만으로는 놓쳤을 실사용 버그 2건을 실제로 발견·수정했다:

| 버그 | 발견 방법 | 결과 |
|---|---|---|
| 375px 뷰포트에서 상단바 테마 토글·프로필/로그아웃 드롭다운이 99px 화면 밖으로 밀려 완전히 접근 불가 | `getBoundingClientRect()`로 `.topbar-right` 좌표 실측 — 시각적으로는 스크린샷 다운스케일 때문에 놓치기 쉬웠음 | `AdminTopbar.css`에 `min-width: 0` 등 모바일 미디어쿼리 추가로 수정 |
| `.data-table` 셀 텍스트가 좁은 화면에서 줄바꿈되어, 이미 구현되어 있던 `overflow-x: auto` 가로 스크롤 패턴이 무력화됨 | 회원 목록 페이지를 375px로 직접 열어 "이서연"이 3줄로 쪼개져 렌더링되는 것을 스크린샷으로 확인 | `global.css`의 `.data-table td`에 `white-space: nowrap` 추가 |
| `SystemPage`/`StatsPage`가 존재하지 않는 `--color-text-2` 토큰을 참조 | 코드 감사 중 발견(CLAUDE.md가 경고하던 정확히 그 패턴) | `--color-text-tertiary`로 교체 |

세 건 모두 `claude/admin-planning-doc-120dha` 브랜치에 커밋·푸시 완료(`54b2268`).

## 4. 적용 범위와 체크리스트

`design` 스킬을 통한 신규 화면 생성뿐 아니라, 기존 화면을 수정하는 모든 프론트엔드 작업에
아래 체크리스트를 적용한다(CLAUDE.md "Working Rules"의 검증 원칙과 정합):

- [ ] `npm run build` 통과 + eslint 경고 0개
- [ ] dev 서버 기동 후 Playwright로 실제 렌더 결과 스크린샷 확인 (생략 불가)
- [ ] 레이아웃/CSS 변경이 있는 경우 375px(모바일) 뷰포트도 확인
- [ ] 다크모드(`data-theme="dark"`) 스크린샷도 색상이 관련된 변경일 경우 확인
- [ ] 문제 발견 시 코드 수정 → 재확인까지 마친 뒤에만 완료로 보고

## 5. 하지 않는 것 (범위 제외)

- **Taste Skill 대응**: 마켓플레이스에 동일 이름의 스킬은 없음을 확인했고, 가장 근접한 대체재로
  `Design` 플러그인(디자인 비평·시스템 관리·접근성 감사 등) 설치를 사용자에게 제안한 상태 —
  설치 여부는 사용자 판단, 본 기획서에서 강제하지 않는다.
- **Image to Code**: 별도 설치 없이 이미 사용 가능한 Claude의 멀티모달 능력이므로 워크플로우
  변경 대상이 아니다. 디자인 레퍼런스 이미지를 받았을 때 1단계(UNDERSTAND)에서 그대로 활용하면
  충분하다.
- 디자인 시스템 토큰 자체의 변경, 새 컴포넌트 라이브러리 도입은 이 문서의 범위가 아니다.
