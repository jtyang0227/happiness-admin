# UI/UX 개선 기획서

> **작성**: Pomelli (기획)
> **작성일**: 2026-08-19
> **범위**: 정보구조 · 워크플로우 · 기능 완성도 (비주얼 디자인 제외 — 4차 와도트 리스킨은 완료 상태이며 본 문서에서 다루지 않음)
> **조사 방법**: `App.jsx` 라우트 22개 전수 조사, `pages/*.jsx` 코드 리딩, 백엔드 컨트롤러 19개 API 표면 대조, 22개 화면 실 렌더링 스크린샷 검토

## 1. 조사 요약

Happiness Admin은 회원·사진·시리즈·포트폴리오·문의라는 핵심 5대 도메인 위에, 최근 신고/공지/배너/팝업/작가인증/갤러리순서/피처드/콘텐츠정책이라는 8개의 운영 도구가 추가되어 총 16개(+정렬 서브메뉴)의 최상위 메뉴를 가진 상태다. 기능 자체는 대부분 잘 동작하지만, **기능이 늘어난 속도만큼 화면 간 연결·정보 우선순위·상태 관리가 따라가지 못한 흔적**이 전반에서 발견된다.

핵심 발견 5가지:

1. **대시보드의 "촬영 예약" 섹션(캘린더·주간목록·KPI 카드 2개)이 전부 죽은 링크다.** `/bookings` 라우트 자체가 없어 클릭하면 사이드바까지 사라지는 404로 튕겨나간다. 백엔드는 목록 조회 API까지 이미 구현되어 있는데 소비하는 화면이 없다.
2. **신고 관리(모더레이션) 워크플로우에 "신고당한 콘텐츠를 실제로 보는" 단계가 없다.** 목록에도, 검토 모달에도 "회원 #8" "사진 #7" 같은 텍스트 배지만 있고 클릭·미리보기가 불가능해, 관리자가 내용을 확인하지 않은 채 삭제·정지 같은 강한 조치를 결정해야 하는 구조다.
3. **"정렬(순서 변경)"이라는 동일한 개념이 화면마다 다른 자리·다른 상호작용으로 4번 따로 구현되어 있다.** 사이드바 아코디언(전체 사진/시리즈 정렬), 독립 사이드바 메뉴(작가별 갤러리 순서), 목록 페이지 내 컨텍스트 링크(시리즈 상세·포트폴리오 아이템), 리스트 내 인라인 화살표·드래그핸들(배너/팝업/피처드) — 관리자가 "정렬하려면 어디로 가야 하는지" 매번 다시 학습해야 한다.
4. **대시보드 KPI의 증감률(%)·진행률 바, 상단바의 "시스템 정상" 배지가 실제 데이터와 연결되어 있지 않다.** 코드상 하드코딩된 고정값이라 시스템 장애 시에도 항상 정상으로 표시되고, 트렌드 수치는 매번 동일하게 노출되어 관리자의 판단을 오도할 수 있다.
5. **회원 상세 페이지가 회원의 전체 상태를 보여주지 못한다.** 포트폴리오 개수는 KPI로 보여주면서 탭이 없고, 작가 인증 상태는 텍스트로만 있고 인증 심사 화면으로 연결되지 않으며, 권한(역할) 변경도 상세 화면에서 불가능해 목록으로 돌아가야 한다.

이 외에도 통계 페이지의 파이 차트에 범례가 없고, 사진 카드에 원시 카테고리 코드가 그대로 노출되며, 커맨드 팔레트(⌘K)가 "회원 검색"을 표방하지만 실제로는 고정 페이지 이름만 검색하는 등 **"약속한 기능과 실제 동작 사이의 간극"**이 여러 화면에서 반복적으로 나타난다.

## 2. 발견한 문제들

### 2.1 대시보드 "예약" 섹션 전체가 죽은 기능

- **현상**: 대시보드는 KPI 카드 2개("오늘 예약", "미확정 예약"), 예약 캘린더 위젯, "이번 주 촬영 예약" 테이블까지 페이지의 상당 부분(스크롤 기준 절반 가까이)을 예약 관련 콘텐츠에 할애한다. 이 모든 요소의 "전체 보기"/"예약 관리에서 보기" 링크, KPI 카드 클릭이 전부 `/bookings`를 가리키는데, `App.jsx`에는 해당 라우트가 정의되어 있지 않아 사이드바·헤더가 전혀 없는 404 화면으로 이동한다.
- **왜 문제인가**: 관리자 입장에서 대시보드 대부분을 차지하는 기능이 클릭할 때마다 막다른 길이다. 신뢰가 깨지고, 대시보드 전체의 완성도에 대한 의구심으로 번진다. 백엔드(`AdminBookingController`)에는 목록(`GET /admin/bookings`, 날짜·상태 필터·페이지네이션 포함)까지 이미 구현되어 있어 프론트 미구현만 남은 상태다.
- **개선 방향**: `/bookings` 예약 관리 페이지 신설(목록 조회 + 날짜/상태 필터, 이미 있는 백엔드 API 그대로 소비 가능). 다만 백엔드에 예약 상태 변경(확정/거절/취소) API가 없으므로 "조회 전용"으로 시작할지, 상태 변경까지 포함할지는 별도 백엔드 논의가 필요하다. 최소한의 임시조치로 링크를 비활성화하거나 "준비 중" 처리해 죽은 링크부터 없애야 한다.
- **영향 화면/컴포넌트**: `DashboardPage`, `BookingCalendar`, `WeeklyBookingList`, 사이드바(예약 메뉴 항목 자체가 없음), `NotFoundPage`.

### 2.2 신고 처리 워크플로우에 "대상 콘텐츠 확인" 단계 부재

- **현상**: 신고 관리 목록의 "대상 유형" 컬럼은 `회원 #8`, `사진 #7`, `시리즈 #6` 같은 텍스트 배지로만 표시된다. "검토" 버튼을 눌러 여는 처리 모달에서도 "대상: 사진 #4" 텍스트만 있을 뿐, 실제 사진·회원 프로필·시리즈 내용을 확인할 방법이 전혀 없다.
- **왜 문제인가**: 모더레이션의 본질은 "신고된 콘텐츠가 실제로 정책을 위반했는지 확인 후 조치"인데, 지금 구조로는 확인 없이 조치(콘텐츠 숨김/삭제, 작성자 경고/정지)를 내려야 한다. 오조치·과잉조치 위험이 매우 크고, 관리자가 결국 다른 탭에서 회원/사진 관리로 가서 ID로 직접 찾아야 하는 이중 작업이 발생한다.
- **개선 방향**: 신고 대상 배지를 실제 리소스로 이동하는 링크로 전환(회원 → 회원 상세, 사진/시리즈 → 해당 상세 미리보기). 처리 모달 안에는 최소한 대상의 썸네일/제목/작성자 같은 요약 정보를 함께 노출해, 새 탭을 열지 않고도 판단 근거를 볼 수 있게 해야 한다.
- **영향 화면/컴포넌트**: `ReportListPage`(목록 테이블, 검토 모달).

### 2.3 "정렬" 기능의 진입점이 4곳으로 분산되고 상호작용도 제각각

- **현상**:
  - 사이드바 "정렬 관리" 아코디언 하위에 `사진 정렬`(전체 사진 대상 글로벌 순서), `시리즈 정렬`이 있음.
  - 사이드바 최상위에 별도로 `갤러리 순서` 메뉴가 있는데, 이는 "작가를 선택하면 그 작가의 사진만 드래그 정렬"하는 기능 — 사진 정렬과 대상 범위만 다를 뿐 개념적으로 동일한 기능.
  - 시리즈 목록의 각 행 "사진 정렬" 버튼, 포트폴리오 목록의 아이템 정렬 링크는 컨텍스트 진입(정렬 관리 그룹에 속하지 않음).
  - 배너 관리는 인라인 상/하 화살표 버튼, 피처드는 동일하게 상/하 화살표, 팝업 관리는 드래그 핸들 아이콘 — 셋 다 "리스트 순서 변경"이라는 같은 작업인데 상호작용 방식이 서로 다름.
- **왜 문제인가**: "정렬"이라는 하나의 멘탈 모델에 대해 관리자가 매번 다른 화면 구조와 다른 조작 방식을 학습해야 한다. 특히 "사진 정렬"과 "갤러리 순서"는 이름만 봐서는 무엇이 다른지, 실제 앱 노출 순서에 어느 쪽이 우선하는지 알기 어렵다.
- **개선 방향**: (a) "사진 정렬" vs "갤러리 순서"가 실제로 서로 다른 데이터(전체 순서 vs 작가별 순서)를 다루는 것인지 먼저 정의하고, 다르다면 하나의 화면에서 범위를 전환하는 방식으로 통합하거나 최소한 사이드바 상에서 같은 그룹으로 묶어야 한다. (b) 배너/팝업/피처드처럼 "짧은 리스트를 재배치"하는 화면들은 상/하 버튼이든 드래그든 하나의 상호작용 패턴으로 통일해야 한다(구체 컴포넌트 설계는 디자이너 영역이므로 본 문서에서는 "통일이 필요하다"는 요구사항만 명시).
- **영향 화면/컴포넌트**: 사이드바 IA 전체, `SortPhotosPage`, `GalleryOrderPage`, `SortSeriesPage`/`SortSeriesDetailPage`, `SortPortfolioPage`, `BannerPage`, `PopupPage`, `FeaturedPage`.

### 2.4 대시보드/상단바에 신뢰할 수 없는 정적(하드코딩) 지표

- **현상**: 대시보드 KPI 카드 6개의 증감률(%, 예: "+12%", "-3%")과 진행률 바(progress)는 API 응답이 아니라 컴포넌트 코드에 상수로 박혀 있다. 상단바의 "● 시스템 정상" 배지도 실제 `/admin/system/status` 헬스체크와 무관하게 항상 초록/정상으로 고정 출력된다(정작 `SystemPage`는 같은 API를 제대로 호출해 보여주고 있어 배지만 따로 논다).
- **왜 문제인가**: 관리자 대시보드에서 지표는 의사결정의 근거인데, 지금은 새로고침해도 항상 같은 숫자가 나오는 가짜 트렌드다. 실제 시스템 장애 상황에서도 헤더는 계속 "정상"이라고 말하므로 오히려 위험 신호를 감추는 역효과가 난다.
- **개선 방향**: 증감률은 실제 기간 대비 API 응답으로 계산하거나, 계산할 데이터가 없다면 표시 자체를 제거한다(가짜보다 없는 편이 낫다). 상단바 상태 배지는 `SystemPage`가 이미 쓰는 API를 재사용해 실제 상태를 반영한다.
- **영향 화면/컴포넌트**: `DashboardPage`(KpiCard), `AdminTopbar`.

### 2.5 회원 상세 페이지의 정보·액션이 목록/다른 화면과 분절됨

- **현상**: 회원 상세의 KPI 그리드는 사진·시리즈·문의·**포트폴리오** 4개 수치를 보여주지만, 탭은 "활동요약/사진/시리즈/문의" 4개뿐이라 포트폴리오는 숫자만 보고 실제 목록을 볼 방법이 없다. "작가 인증" 항목은 "미인증" 텍스트만 있을 뿐 인증 심사(승인/반려) 화면으로 연결되지 않아, 별도로 사이드바의 "작가 인증" 메뉴에서 이름으로 다시 찾아야 한다. "권한" 필드도 읽기 전용 텍스트라 역할을 바꾸려면 회원 목록으로 돌아가야 한다.
- **왜 문제인가**: 회원 상세는 한 회원에 대해 "지금 이 자리에서" 판단·조치하는 화면이어야 하는데, 실제로는 조회 전용에 가깝고 조치는 목록이나 다른 메뉴로 이동해야 가능하다. 컨텍스트 전환이 잦아지고, 회원 하나를 처리하는 데 여러 화면을 오가야 한다.
- **개선 방향**: 포트폴리오 탭 추가(백엔드 포트폴리오 조회 API에 회원 필터 파라미터 추가 필요), 작가 인증 섹션에 해당 회원의 인증 신청 건으로 바로 연결되는 링크 또는 그 자리에서 승인/반려 가능하도록 확장, 권한 변경을 상세 화면에서도 가능하게 만든다.
- **영향 화면/컴포넌트**: `MemberDetailPage`, `MemberListPage`(권한 변경 UI와의 일관성), `VerificationListPage`(회원 상세와의 연결).

### 2.6 커맨드 팔레트(⌘K)가 실제 기능보다 과장된 약속을 함

- **현상**: 상단바 검색창의 플레이스홀더는 "페이지, 회원, 기능 검색..."이라고 명시하지만, 실제 `CommandPalette` 컴포넌트는 고정된 16개 페이지 이름 목록만 필터링한다. 회원 이름, 사진 제목 등 실제 데이터를 검색해 해당 상세로 이동하는 기능은 없다.
- **왜 문제인가**: 반복 업무(특정 회원 찾기, 특정 문의 찾기)가 잦은 운영 도구에서 전역 검색은 가장 기대되는 기능 중 하나다. 지금은 이름만 그럴듯하고 실제로는 사이드바 메뉴를 다시 나열한 것에 불과해, 기대와 실망의 격차가 크다.
- **개선 방향**: 최소 범위로 회원 이름/이메일 검색 결과를 팔레트에 포함시키는 것부터 시작(기존 `/admin/members?search=` API 재사용 가능). 이후 사진·문의 등으로 확장할지는 사용 빈도를 보고 결정.
- **영향 화면/컴포넌트**: `AdminTopbar`, `CommandPalette`.

### 2.7 문의 상태가 "읽음/미읽음" 2단계뿐, 실제 처리 여부 추적 불가

- **현상**: 문의 관리는 각 문의를 읽음/미읽음으로만 구분한다. 실제로 해당 문의에 답장했는지, 예약으로 이어졌는지, 종결됐는지를 나타내는 상태가 없다.
- **왜 문제인가**: "읽었다"는 것과 "처리했다"는 것은 다른 의미인데 하나로 뭉뚱그려져 있어, 미읽음만 0이 되면 마치 모든 문의가 처리 완료된 것처럼 보이는 착시가 생긴다. 특히 여러 관리자가 나눠서 문의를 처리하는 상황이라면 중복 응대나 누락이 발생하기 쉽다.
- **개선 방향**: "읽음" 외에 "처리 완료/보류" 같은 별도 상태 필드 도입 검토(백엔드 상태값 확장 필요). 최소한 프론트에서만이라도 관리자 메모 필드를 추가해 처리 이력을 남길 수 있게 하는 것도 대안.
- **영향 화면/컴포넌트**: `InquiryListPage`, 관련해 대시보드의 "최근 문의" 테이블도 동일한 상태 체계를 따르게 됨.

### 2.8 사진 카드에 원시 카테고리 코드가 해석 없이 노출

- **현상**: 사진 관리 목록 카드에는 좌상단/우상단에 색채무드 뱃지와 함께 `01`, `02` 같은 2자리 코드, 카드 본문 하단에는 `0101010101` 같은 10자리 코드가 그대로 표시된다. 일부는 `l1Name`/`l2Name` 한글 라벨 뱃지로 보완되지만, 코드 뱃지 자체는 해석 없이 숫자만 노출된다.
- **왜 문제인가**: 5단계 분류 코드 체계(1차~5차, 각 2자리)를 관리자가 외우고 있지 않는 이상 목록 단계에서는 의미를 알 수 없다. 슬라이드오버를 열어야 비로소 각 자리의 한글 이름을 볼 수 있어, 목록에서 "이 사진이 어떤 카테고리인지" 한눈에 스캔하는 목적을 달성하지 못한다.
- **개선 방향**: 목록 카드 단계에서부터 코드가 아닌 사람이 읽을 수 있는 라벨(또는 라벨+코드 병기)로 통일 표시.
- **영향 화면/컴포넌트**: `PhotoListPage`(카드 그리드), `SortPhotosPage`/`SortSeriesDetailPage`(사진 정렬 목록에서도 "Photo ID: 22" 같은 내부 ID가 그대로 노출).

### 2.9 통계 페이지 파이 차트에 범례 없음

- **현상**: "색채 무드 분포" 파이 차트가 6개 색 조각으로만 그려지고, 어떤 색이 어떤 무드(WARM/COOL/…)를 의미하는지 알려주는 범례나 라벨이 화면에 없다.
- **왜 문제인가**: 차트가 정보 전달이 아니라 장식으로만 기능한다. 관리자가 이 차트를 보고 내릴 수 있는 결정이 사실상 없다.
- **개선 방향**: 각 조각에 무드 이름과 비율(%) 또는 수치를 함께 표기하는 범례 추가가 필요하다(구체적 배치·스타일은 디자이너 영역).
- **영향 화면/컴포넌트**: `StatsPage`(색채 무드 분포 차트).

### 2.10 대시보드와 통계 페이지의 콘텐츠 중복으로 화면 역할이 불분명

- **현상**: 대시보드에 "최근 7일 사진 업로드" 차트와 "인기 사진 TOP 5"가 있고, 통계 페이지에도 기간별 추이 차트와 "인기 사진 TOP 10"이 거의 동일한 형태로 다시 나온다.
- **왜 문제인가**: 두 화면이 같은 정보를 범위(5개/10개, 7일 고정/7·30·90일 선택)만 다르게 반복해서 보여줘, "대시보드는 요약, 통계는 상세"라는 원칙이 있다면 그 경계가 흐릿하다. 사용자는 어느 화면을 먼저 봐야 하는지 헷갈리고, 유지보수 시 두 곳을 같이 고쳐야 하는 부담도 생긴다.
- **개선 방향**: 대시보드는 "오늘 당장 확인해야 할 이상 신호·액션 필요 항목" 중심으로, 통계는 "기간별 추이 분석" 중심으로 각 화면의 역할을 명확히 재정의하고 중복 위젯을 정리한다.
- **영향 화면/컴포넌트**: `DashboardPage`, `StatsPage`.

### 2.11 포트폴리오/시리즈 목록에 우선순위 판단 정보 부족

- **현상**: 포트폴리오 목록은 상태별(임시저장/심사중/승인/반려) 카운트 카드가 있지만, "심사 중" 항목이 얼마나 오래 대기 중인지(경과일)는 표시되지 않는다. 시리즈 목록도 커버·사진 수·생성일 외에 좋아요/조회 등 콘텐츠 우선순위를 가늠할 지표가 없다.
- **왜 문제인가**: 심사 대기가 여러 건 쌓였을 때 어떤 것부터 처리해야 하는지(오래 기다린 순 등) 판단 근거가 없어, 정렬 순서(현재는 최신순 고정으로 보임)에만 의존하게 된다.
- **개선 방향**: 심사 중 항목에 "대기 경과일" 또는 "접수일" 정렬 옵션 제공, 시리즈 목록에 참여도 지표(좋아요·조회) 컬럼 추가 검토.
- **영향 화면/컴포넌트**: `PortfolioListPage`, `SeriesListPage`.

### 2.12 이미지 중심 화면 전반에서 썸네일이 표시되지 않음

- **현상**: 사진 관리, 시리즈 관리, 포트폴리오, 배너, 피처드, 통계의 인기 사진 TOP 10 등 이미지가 핵심인 화면 대부분에서 실제 썸네일 대신 회색 플레이스홀더 아이콘만 나열된다(`ImgWithFallback`이 `onError`로 정상 폴백 처리하고 있는 것으로 보아, 원인은 시드 데이터의 이미지 URL이 유효하지 않은 것으로 추정됨).
- **왜 문제인가**: 이 앱은 사진 커뮤니티의 관리 도구인데, 정작 관리자가 사진을 "보고" 판단해야 하는 화면들에서 아무것도 보이지 않는다면 핵심 업무(카테고리 확인, 부적절 콘텐츠 판별, 피처드 선정 등)를 시각적으로 수행할 수 없다. 이번 조사는 개발/시드 데이터 기준이라 실제 운영 데이터에서는 다를 수 있으나, 폴백 UI에 의존하는 비율이 매우 높다면 원인 확인이 필요하다.
- **개선 방향**: 실제(또는 실서비스에 가까운) 이미지 데이터로 재검증 필요. 폴백이 구조적으로 자주 발생하는 상황이라면, 원본 이미지 URL 만료/CDN 접근성 등 데이터 파이프라인 점검을 백엔드팀과 별도로 논의.
- **영향 화면/컴포넌트**: `PhotoListPage`, `SeriesListPage`, `PortfolioListPage`, `BannerPage`, `FeaturedPage`, `DashboardPage`(인기 사진), `StatsPage`(인기 사진 TOP 10), 정렬 관리 화면 전체.

### 2.13 존재하지 않는 라우트로 이동 시 관리자 셸(사이드바/헤더) 이탈

- **현상**: `/bookings`처럼 정의되지 않은 경로로 이동하면 `AdminLayout`(사이드바·상단바) 없이 완전히 독립된 404 화면이 뜬다. "홈으로 돌아가기" 버튼 외에는 사이드바로 즉시 복귀할 방법이 없다.
- **왜 문제인가**: 로그인 상태의 관리자가 잘못된 링크를 눌렀을 뿐인데 마치 로그아웃되거나 앱을 벗어난 것 같은 경험을 준다. 최소한 관리자 셸 안에서 "페이지를 찾을 수 없다"는 메시지를 보여주는 것이 맥락 유지에 유리하다.
- **개선 방향**: 인증된 사용자의 404는 `AdminLayout` 내부에서 렌더링해 사이드바·헤더를 유지하도록 라우팅 구조 조정.
- **영향 화면/컴포넌트**: `NotFoundPage`, `App.jsx` 라우팅 구조.
