# 개인정보 보호 강화 기획 — 암호화 · 최소 노출 · 접속기록

> **작성**: 2026-10-21 · 기획(Pomelli 기준) → 구현(Claude Code)
> **근거 법령**: 「개인정보 보호법」 제29조(안전조치의무), 「개인정보의 안전성 확보조치 기준」(개인정보보호위원회 고시, 2023-09-22 통합 개정본 · 2025-10-31 일부 개정 시행)
> ⚠️ 조문은 공개 해설 자료로 확인했다. 최종 적용 전 국가법령정보센터 원문과 사내 개인정보 보호책임자 검토를 거칠 것.

## 1. 법적 요구사항 정리 — 이 서비스에 무엇이 해당하나

| 고시 조항 | 요구 | 이 서비스 해당 여부 |
|---|---|---|
| 제7조① 인증정보 | 비밀번호 등 인증정보는 저장·송수신 시 암호화, **비밀번호는 일방향 암호화** | 해당 — 회원 비밀번호. **BCrypt로 이미 일방향 저장** ✅ |
| 제7조② 이용자 개인정보 | 주민등록번호·여권번호·운전면허번호·외국인등록번호·신용카드번호·계좌번호·생체인식정보는 저장 시 암호화 | **해당 없음** — 이런 정보를 저장하지 않는다(코드 전수 확인). 앞으로 추가하면 반드시 암호화 |
| 제7조 송수신 | 인증정보·개인정보를 정보통신망으로 송수신 시 암호화 | 해당 — 운영 배포는 HTTPS(Railway·Vercel). 로그인 비밀번호는 TLS 위에서만 전송 |
| 제5조 접근권한 | 업무 수행에 필요한 최소한으로 권한 부여 | 해당 — 비로그인 공개 API가 회원 개인정보를 반환하던 결함(§2 F1) |
| 제6조 접근통제 | 불법 접근 방지, 일정 시간 미사용 시 **자동 접속 차단** | 해당 — 관리자 화면에 유휴 차단이 없었음, 로그인 무차별 대입 제한 없음 |
| 제8조 접속기록 | 개인정보취급자의 접속기록(계정·접속일시·접속지·처리한 정보주체·수행업무) **1년 이상 보관**(5만명 이상·고유식별/민감정보 처리 시 **2년 이상**), 위·변조 방지, 접속기록·**다운로드 확인/점검** 절차를 내부 관리계획으로 정해 이행 | 해당 — 개인정보 열람·다운로드 기록이 없었음 |

**결론**: 법이 저장 암호화를 *강제*하는 항목(고유식별정보·카드·계좌·생체)은 현재 없다. 이메일·전화번호·이름은
암호화 의무 대상이 아니다. 따라서 "가장 안전한 방법"은 **의무 항목 준수 + 실제 유출 경로 차단 + 다층 방어**로 정의한다.

| # | 결함 | 확인 | 심각도 |

## 3. 설계 원칙 — 공유 DB 제약

운영에서 Admin은 App과 **같은 Postgres**를 쓴다. `members.email/tel/name`은 App이 로그인·화면에 평문으로 읽으므로
Admin이 일방적으로 암호화하면 **App 로그인이 깨진다**. 그래서:

- **App 공유 컬럼**(이메일·전화·이름): 저장 형태는 건드리지 않고 **Admin 쪽 노출을 최소화**(마스킹 기본 + 사유 입력 후 열람 + 접속기록).
  저장 암호화가 필요해지면 App과 함께 "암호문 + 검색용 HMAC 블라인드 인덱스" 이중 컬럼 방식으로 이관해야 한다(§6 후속).
- **Admin 소유 데이터**(`admin_member_notes.content`, `members.suspend_reason` — App 엔티티에 없는 Admin 추가 컬럼): **AES-256-GCM 필드 암호화**.

## 4. 구현 내용

### 4-1. 긴급 차단 (F1·F2·F3)
- 공개 경로를 `POST /api/auth/login`, `POST /api/auth/admin/login`, 앱 공개 팝업, 헬스체크로 **화이트리스트 축소**. 회원가입·이메일 확인·회원 조회·OAuth 엔드포인트 **삭제**(Admin은 회원가입 주체가 아님).
- 로그인 오류 메시지 단일화("이메일 또는 비밀번호가 올바르지 않습니다"), 존재하지 않는 계정도 BCrypt 비교를 수행해 **응답 시간 차이로 계정 추측 방지**.
- **같은 이메일 5회 연속 실패 시 15분 잠금**(인메모리, 단일 인스턴스 기준).

### 4-2. 필드 암호화 (F6)
- `FieldEncryptor`: AES-256-GCM, 매 암호화마다 12바이트 랜덤 IV, 저장 형식 `enc:v1:<base64(iv‖ciphertext‖tag)>`.
- JPA `AttributeConverter`로 투명 적용. 접두어 없는 기존 평문은 그대로 읽고(무중단 이관), 다음 저장 시 암호화.
- 키: 환경변수 `PRIVACY_ENCRYPTION_KEY`(Base64 32바이트). **prod 프로필에서 키가 없으면 기동 실패**, dev는 고정 개발용 키 + 경고 로그.

### 4-3. 최소 노출 (F4·F5)
- 회원 목록·상세·뉴스레터 목록의 이메일·전화번호를 서버에서 **마스킹해서 응답**(`us***@test.com`, `010-****-0002`). 검색은 서버에서 원문으로 계속 동작.
- 회원 상세 "개인정보 보기": **열람 사유 필수** → 원문 반환 + 접속기록.
- 모든 CSV 내보내기에 **다운로드 사유 필수**, 건수와 함께 접속기록.
- 활동 로그 상세에 이메일 원문을 남기지 않음.

### 4-4. 개인정보 접속기록 (제8조)
- 신규 테이블 `admin_privacy_access_logs`: 계정(관리자 id·이름), 접속일시, 접속지(IP), 처리한 정보주체(회원 id 또는 건수), 수행업무(`LIST`/`VIEW`/`REVEAL`/`EXPORT`/`INSPECTION`), 사유.
- **위·변조 방지**: 각 행에 `SHA-256(이전 해시 ‖ 행 내용)` 해시 체인. 검증 API가 끊긴 지점을 찾아낸다. 수정·삭제 API 없음.
- **보관**: 삭제 로직 없음(2년 이상 보관 요건 충족, 파기 정책은 내부 관리계획으로).
- **점검**: `/privacy-logs` 화면(웹관리자 전용) — 기간·업무·관리자 필터, 무결성 검증, "점검 완료" 기록 남기기, 다운로드 내역 강조.

### 4-5. 접근통제 (F7)
- 관리자 화면 **30분 무조작 시 자동 로그아웃**(5분 전 안내 없이 즉시 — 단순·확실).
- JWT 기본 만료 24시간 → **8시간**.

## 5. 수용 기준
- [x] 비로그인 `GET /api/auth/member/{id}`·`/signup`·`/check-email` → 401/403
- [x] 없는 이메일·틀린 비밀번호 응답 메시지 동일, 6번째 시도부터 잠금
- [x] DB의 메모·정지 사유가 `enc:v1:` 암호문, 화면에는 평문, 기존 평문 행도 읽힘
- [x] 목록·상세 응답에 이메일·전화 원문 없음, 사유 입력 후 열람 시 원문 + 접속기록
- [x] 내보내기 사유 없으면 400, 있으면 접속기록에 건수·사유
- [x] 접속기록 해시 체인 검증 OK, 행을 임의로 바꾸면 검증 실패 지점 표시
- [x] SA는 접속기록 화면 접근 불가(403), 30분 유휴 시 로그아웃

## 5-1. 구현 결과 (2026-10-21)

- 수용 기준 전부 curl·브라우저·자동 테스트로 확인(신규 테스트 13개: 암호화 왕복·IV 무작위·변조 탐지·prod 키 누락 기동 실패·마스킹·로그인 잠금·DB 원본이 암호문인지·평문 이관 행 읽기·접속기록 변조 탐지).
- 존재하지 않는 계정/틀린 비밀번호 응답 시간 동일(약 0.10초).
- 진행 중 발견해 고친 것: 유휴 검사 전에 활동을 먼저 기록해 오래 방치된 세션이 살아나던 문제, 프로필명이 `@@user2`로 이중 표시되던 문제.
- 개발 모드에서 상세 조회 접속기록이 2건씩 남는 것은 React StrictMode의 이중 effect 때문이며 운영 빌드에서는 1건.
- **배포 주의**: Railway에 `PRIVACY_ENCRYPTION_KEY`를 먼저 설정해야 한다(없으면 기동 실패 — 의도된 fail-fast).

## 6. 후속 과제 (이번 범위 밖)
1. **App 공유 컬럼 저장 암호화**: App·Admin 공통 키로 `email_enc`·`email_hmac`(검색용) 이중 컬럼 이관 — App 저장소 변경 필요.
2. 다중 인스턴스 배포 시 로그인 잠금을 Redis 등 공유 저장소로.
3. 키 관리: 운영 키를 KMS/시크릿 매니저로, 키 교체 시 `enc:v2:` 재암호화 배치.
4. 관리자 외부 접속 시 2단계 인증(제6조② 안전한 인증수단).
